## 0. 이 사이트가 존재하는 이유

HypeConnect의 근본 목적은 **"점주가 돈을 내고, 게스트가 실제로 방문해 후기를 남기는 거래"를 반복 가능하게 만드는 것**이다.

| 이해관계자 | 얻는 것 | 사이트가 해 줘야 하는 일 |
|---|---|---|
| 점주(혼술바·소셜파티 업체) | 손님 방문 + 리뷰 노출 | 파티를 올리고, 방문한 만큼만 수수료를 낸다 |
| 게스트(체험단) | 혜택(무료·할인) 받고 참여 | 파티를 찾아 신청하고, 선정되면 방문하고 미션을 낸다 |
| 운영자(우리 2명) | 방문당 수수료(약 1만 원) | 모집·선정·방문 인증·정산을 적은 손으로 처리한다 |

그래서 기능의 우선순위는 **신뢰(가짜가 아님) → 거래 흐름(신청~정산) → 운영 효율 → 편의** 순이다. Notion 마일스톤 기준으로 지금은 M4(업체·체험단 확보, 11/16~19)이고, M5(11/20~24)에 실거래 20건을 검증해야 한다.

## 2. 1단계(최우선): 목업 + 실데이터 하이브리드 → DB 순차 채우기

### 2.1 요청 검토 결과

> "예전 목업과 하이브리드로 먼저 채우고, DB를 하나씩 채워 넣는 것이 구현 가능한가?"

**가능하다. 다만 "목업을 진짜처럼 보여 주는" 방식은 안 되고, "예시임을 표시한 쇼케이스"로 해야 한다.** 이유:

1. **기술적으로 쉽다.** 목업 데이터(`js/party-data.js`의 파티 8건)는 이미 서버 파티와 같은 모양(`normalizeServerParties` 결과)이다. 서버 목록 뒤에 예시 카드를 붙이고 `isSample` 표시만 추가하면 된다. 서버·DB 변경 없음. 웹 파일 2개(`index.html`, `party-connect/index.html`)와 `js/party-api.js` 수준의 작업.
2. **예시 파티에 신청이 들어가면 안 된다.** 예시 파티는 DB에 없어서 신청 API가 실패한다. 버튼을 "신청 오픈 예정"으로 막아야 게스트가 헛걸음하지 않는다.
3. **법적·신뢰 위험이 있다.** 현재 목업에는 실제 상호처럼 보이는 이름(예: "솔로몬클럽 양재본점", 제휴 파트너 목록의 실존 업체명)과 **실제 사람이 쓴 것처럼 보이는 후기**가 있다. 제휴하지 않은 업체를 파트너로 표시하거나 가짜 후기를 진짜처럼 노출하면 표시·광고 관련 법(거짓·과장 광고, 소비자 오인)과 상표 문제가 생길 수 있고, 무엇보다 첫 점주·게스트의 신뢰를 잃는다. 우리 운영 원칙("허위 영수증 금지")과도 같은 맥락이다.
4. **DB는 목업으로 채우지 않는다.** 가짜 점포·파티를 운영 DB에 넣으면 신청·원장이 섞이고(원장은 삭제 불가), 정산 대조가 깨진다. DB에는 **실제 계약한 점포와 실제 열릴 파티만** 넣는다.

## 5. 보완점 (지금 바꾸면 효과가 큰 것)

1. **사이트가 비어 보이는 문제** → 2장의 하이브리드. 가장 먼저.
2. **게스트가 결과를 모른다** → 선정·반려·보완 요청을 알릴 방법이 없다. 자동화 전까지는 관리자 화면에서 연락처 복사 + 문자 템플릿(M-11)으로 운영자가 직접 알린다.
3. **미션 조건이 안 보인다** → 게스트가 "무엇을 올려야 하는지" 모르고 신청한다. 상세·마이페이지에 표시(G-06).
4. **잔액 부족을 최종 승인 때 안다** → 점주가 미리 충전하지 않으면 미션까지 끝낸 게스트의 정산이 막힌다. 선정 단계에서 경고(M-13).
5. **공개 화면의 신뢰 문제** → 실존 업체명, 가짜 후기, 미구현 혜택 배너(F0-2, F0-3).
6. **약관·처리방침 본문이 없다** → 동의를 받는데 내용을 보여 주지 못한다(L-01). 법적으로 가장 먼저 채워야 한다.
7. **장애를 늦게 안다** → 배포 후 자동 확인과 오류 알림(L-04, L-05).
