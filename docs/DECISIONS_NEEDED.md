## A. 사이트 첫인상·쇼케이스 (1단계 하이브리드)

### Q-01. 실제 파티가 몇 건 미만일 때 예시 파티를 보여 줄까? — P0
- **예시 답변:** 공개 중인 실제 파티가 **6건 미만이면 예시 파티로 채워 화면에 최소 6건**이 보이게 한다. 실제 파티는 항상 예시보다 앞에 둔다. 실제가 6건 이상이면 예시는 모두 숨긴다.
- **이유:** 6건이면 데스크톱 3열 기준 두 줄, 모바일에서는 첫 화면과 한 번 스크롤 분량이라 "비어 있다"는 인상을 없애기에 충분하다. 그보다 많으면 예시가 실제 파티를 가린다. 자동으로 줄어드는 방식이라 운영자가 따로 끌 필요가 없다.
- **결정 (2026-11-15):** 예시 답변대로. 기준값 6은 코드에서 상수로 두어 바꾸기 쉽게 한다.

### Q-02. 예시 파티의 업체명·사진은? 실제 협의 중인 업체 이름을 써도 되나? — P0
- **예시 답변:** 예시는 **가명 + "(예시)"**("OO 혼술바 (예시)", 지역은 실제 상권 이름 사용 가능)으로 한다. 주소는 "서울 강남구 일대"처럼 구역만 쓴다. 사진은 상업적 이용이 허락된 무료 이미지를 **우리 저장소 `assets/`에 내려받아** 쓴다. 실제 업체 이름은 **그 업체의 명시적 동의(메시지·메일 기록)가 있을 때만** 쓴다.
- **이유:** 계약하지 않은 실존 업체 이름을 쓰면 그 업체와 제휴한 것처럼 보여서 소비자 오인과 상표 문제가 생길 수 있다. 무엇보다 그 업체가 직접 보면 영업이 어려워진다. 현재 목업 이미지 일부는 **다른 프로젝트의 Supabase 스토리지**를 참조해서, 그 프로젝트가 지우면 사진이 깨진다. 우리 저장소에 두면 이 의존이 없어진다.
- **결정 (2026-11-15):** 예시 답변대로.

### Q-03. 예시 파티에서 게스트가 누르는 버튼은? — P0
- **예시 답변:** 버튼 문구는 **"신청 오픈 예정"이고 누를 수 없다.** 카드와 상세 모두 "예시" 배지를 붙이고, 상세 하단에 "제휴 매장이 확정되면 실제 파티로 열려요"라고 한 줄 안내한다. 찜과 공유 버튼은 숨긴다.
- **이유:** 예시 파티는 DB에 없어서 신청하면 서버 오류가 난다. "오픈 알림 받기"는 연락처를 새로 모으는 일이라, 처리방침 본문(L-01)과 저장소가 먼저 필요하다. 지금 가장 빠르고 안전한 선택은 버튼을 막는 것이다.
- **결정 (2026-11-15):** 예시 답변대로. "오픈 알림 받기"는 L-01 이후 P1로 다시 검토한다.

### Q-04. 메인 "참여 후기" 섹션은? — P0
- **예시 답변:** 실제 완료(COMPLETED)된 게스트가 쓴 후기가 생길 때까지 **섹션을 숨긴다.** 그 자리에는 "이렇게 진행돼요"(신청 → 선정 → 방문 → 미션 → 완료) 3~4단계 안내를 둔다.
- **이유:** 지금 후기는 목업이다. 사람이 쓴 것처럼 보이는 가짜 후기를 공개하면 거짓·기만 광고가 될 수 있다. "예시 후기"라고 붙여도 신뢰를 주지 못하니, 숨기고 이용 방법을 보여 주는 편이 체험단 모집에 더 도움이 된다.
- **결정 (2026-11-15):** 예시 답변대로.

### Q-05. 메인 배너의 "추천인 적립금 2배", "선정 시 무료 초대 티켓"을 실제로 줄 것인가? — P0
- **예시 답변:** **지금은 주지 않는다. 두 배너를 내린다.** 대신 사실만 담은 배너로 바꾼다.
  - "혼술바·소셜파티 체험단 모집 중 — 선정되면 파티 혜택을 무료/할인으로"(혜택 내용은 파티별로 표시)
  - "매장 사장님, 방문한 만큼만 내는 체험단을 시작하세요 → 제휴 문의"
  - 후기 배너("솔직한 평가를 남겨 보세요")는 후기 기능(G-22) 전까지 내린다.
- **이유:** 추천인 적립금은 시스템이 없고, 초대 티켓도 운영 정책이 없다. 없는 혜택을 광고하면 과장 광고이고, 게스트가 요구하면 응대할 방법이 없다. 바꾼 문구는 점주와 게스트 모집이라는 M4 목표에 맞는다.
- **결정 (2026-11-15):** 예시 답변대로.

### Q-06. 파티 사진은 누가 준비하고 어디에 저장할까? — P0
- **예시 답변:** 사진은 **점주에게 받는다.** 받을 때 "HypeConnect 게시 사용 동의"를 메시지로 남긴다. 저장 위치는 **우리 Supabase 프로젝트의 공개 Storage 버킷(`party-images`)**이다.
  - P0: 운영자가 대시보드에 올린 뒤, 관리자 화면의 이미지 URL 칸에 붙여 넣는다(F0-5).
  - P1: 관리자 화면에서 바로 올릴 수 있게 한다.
  - 사진이 없으면 기본 이미지를 쓴다.
- **이유:** 점주 사진이 실제 매장을 가장 정확히 보여 주고, 사용 동의를 남겨 두면 저작권 분쟁이 없다. 같은 Supabase를 쓰면 새 서비스나 비용을 추가하지 않아도 된다. URL 입력은 서버 변경이 거의 없어서(이미 `images` 칸이 있음) M4 전에 끝낼 수 있다.
- **결정 (2026-11-15):** 예시 답변대로. Jacob 승인으로 같은 날 공개 버킷 `party-images`를 만들었다(파일 크기·형식 제한 없음, 업로드 정책 없음 → 대시보드에서만 올릴 수 있음).

## B. 게스트 정책

### Q-07. 카테고리는 혼술바·소개팅·소셜파티 3개로 고정할까? — P1
- **예시 답변:** 3개를 유지한다. 실제 제휴 업체가 3개에 맞지 않을 때만 추가하고, 추가하면 필터와 관리자 입력을 같은 PR에서 고친다.
- **이유:** 업체가 0곳인 지금 카테고리를 늘리면 빈 필터만 생긴다. 소개팅은 "만남 주선"으로 보여 운영 부담이 크니, 첫 제휴는 혼술바와 소셜파티에 집중하는 편이 안전하다.

### Q-08. 게스트 선정 기준은? — P1
- **예시 답변:** 운영자가 판단하되 순서를 정해 둔다. ① 차단·노쇼 이력이 없는 사람 → ② 미션을 낼 수 있는 SNS 계정이 있는 사람(점주 요구 시) → ③ 신청이 빠른 순. 기준 요약은 파티 상세에 공개한다.
- **이유:** 기준이 없으면 탈락한 사람이 불공정하다고 느끼고, 관리자 2명이 서로 다르게 고른다. 선착순만 쓰면 미션을 못 내는 사람이 뽑혀 정산이 안 된다.
- **결정 (2026-11-18):** 예시 답변대로. 선정 기준 3단계를 파티 상세에 공개(`js/party-policy.js` `SELECTION_CRITERIA`).

### Q-09. 연락처 본인 확인이 필요한가? — P1
- **예시 답변:** MVP에서는 하지 않는다. 대신 노쇼 2회면 자동 차단, 같은 연락처로 여러 계정을 만든 경우는 관리자가 수동 차단한다. 실거래 20건 결과를 보고 다시 판단한다.
- **이유:** 휴대폰 인증은 비용과 개발이 들고, 신청 전환율도 떨어뜨린다. 지금 규모에서는 운영자가 선정 단계에서 걸러낼 수 있다.

### Q-10. 선정·반려·보완 요청 결과를 무엇으로 알릴까? — P1
- **예시 답변:** M5까지는 **운영자가 문자로 직접 알린다.** 관리자 화면에 "연락처 복사 + 안내 문구 복사" 버튼(M-11)을 만든다. 카카오 알림톡은 비즈 채널 심사와 비용을 확인한 뒤 M6 이후에 검토한다.
- **이유:** 지금 게스트는 사이트에 다시 들어와야만 결과를 알 수 있어서, 선정돼도 방문하지 않을 위험이 크다. 실거래 20건 규모는 수동으로 충분하다. 자동화는 실제로 몇 건을 보내는지 알고 나서 하는 게 비용 면에서 맞다.

### Q-11. 게스트 개인정보를 얼마나 보관하나? — P1
- **예시 답변:** 신청 정보(이름·연락처·방문 기록)는 **파티 종료 후 1년** 보관 후 파기한다. 탈퇴하면 즉시 파기하되, 정산(원장)과 연결된 거래 기록은 법정 보관 기간 동안 연락처를 지운 상태로 남긴다.
- **이유:** 처리방침(L-01)에 보관 기간을 적어야 한다. 노쇼·분쟁 확인에 1년이면 충분하다. 원장은 삭제할 수 없는 설계라 개인 식별 정보만 지우는 방식이어야 한다. 정확한 법정 기간은 전문가 확인이 필요하다.

### Q-13. 방문 인증 허용 시간(시작 60분 전~종료)을 바꿀까? — P1
- **예시 답변:** 시작 60분 전은 유지하고, 끝은 **종료 후 2시간까지** 늘리는 안을 M5 전에 결정한다. 그전까지는 "방문 인증은 파티 중에 바로 처리"를 운영 규칙으로 안내한다.
- **이유:** 지금은 운영자가 파티가 끝난 뒤 처리하면 인증이 막혀, 실제 방문한 사람이 노쇼가 될 수 있다. 다만 시간을 늘리면 사후 조작 여지도 생기니, 너무 길게 늘리지 않는다.

### Q-16. 노쇼 벌점 기준은 적절한가? — P1
- **예시 답변:** 서버에 이미 있는 규칙(벌점 누적 시 30일 자동 차단)을 유지하고, 신청 화면과 선정 안내 문구에 "선정 후 불참 시 30일간 신청 제한"을 명시한다.
- **이유:** 노쇼는 점주 신뢰를 직접 깎는다. 규칙은 있는데 안내가 없으면 차단된 게스트의 항의가 생긴다.
- **결정 (2026-11-18):** 예시 답변대로. 파티 상세·신청 폼에 "선정 후 불참 시 30일 신청 제한" 안내(`NOSHOW_NOTICE`).

### Q-17. 게스트가 신청을 취소할 수 있는 마감은? — P1

## C. 점주·정산 정책

### Q-12. 사이트에 표시할 사업자 정보는? — P0

- **이유:** 개인정보를 받는 서비스는 처리방침과 책임자를 공개해야 하고, 사업자 정보가 있어야 점주와 게스트가 운영 주체를 믿는다. 통신판매업 해당 여부는 사업 형태에 따라 달라서 단정하지 않는다.
- **결정 (2026-11-15):** 표시 항목은 예시 답변대로. **값(대표자, 사업자번호, 주소)은 Jacob이 제공해야 한다.** 값이 오기 전에는 푸터 틀만 만들고 빈 항목은 숨긴다.
- **보류 (2026-11-15, Jacob):** 값 제공과 통신판매업 확인을 보류한다. L-03 푸터 작업은 값이 올 때까지 시작하지 않는다.

### Q-18. 수수료는 모든 점포 1만 원 고정인가? — P0
- **예시 답변:** **기본 1만 원/인으로 고정한다.** 예외(첫 달 할인, 대형 업체 단가 조정)는 서면 합의가 있을 때만 점포 기본값이나 파티별 수수료로 바꾸고, 그 사실을 점포 메모에 남긴다.
- **이유:** Notion BM이 "방문당 약 1만 원"이고, 단가가 같아야 수익 계산과 정산 대조가 쉽다. 서버는 이미 점포 기본값과 파티별 변경을 지원하므로 예외를 처리할 수단은 있다.
- **결정 (2026-11-15):** 예시 답변대로.

### Q-19. 선불 충전 최소 금액과 환불 규칙은? — P1
- **예시 답변:** 첫 충전은 **최소 5명분(5만 원)**으로 한다. 잔액은 점주가 요청하면 영업일 3일 안에 환불한다. 잔액이 파티 정원보다 적으면 그 파티는 공개하지 않는다(M-13과 연결).
- **이유:** 미션까지 끝낸 게스트의 정산이 잔액 부족으로 막히면 게스트 신뢰가 깨진다. 최소 충전과 공개 전 확인으로 이 일을 줄인다. 환불 기한을 정해 두면 점주의 가입 부담이 낮아진다.

### Q-20. "유효 방문"(수수료가 생기는 시점)의 기준은? — P0
- **예시 답변:** **미션을 최종 승인한 시점에만 수수료를 차감한다.** 방문 인증만 한 상태, 미션 미제출, 노쇼, 반려는 수수료가 없다.
- **이유:** 점주가 원하는 것은 "방문 + 리뷰"이므로, 둘 다 확인된 때만 돈을 받는 것이 Notion BM("방문한 만큼만")과 점주 설득 논리에 맞다. 현재 서버도 이렇게 설계돼 있어 변경이 필요 없다.
- **결정 (2026-11-15):** 예시 답변대로. 점주 계약서·제휴 안내 문구에도 같은 기준을 쓴다.

### Q-21. 미션 검수 기준과 보완 요청 횟수 제한은? — P1
- **예시 답변:** 검수 체크리스트는 ① 링크가 열림 ② 해당 매장 방문 후기임 ③ 점주가 요청한 사진 수·해시태그 충족 ④ 협찬 표시 포함(Q-25)이다. 보완 요청은 **최대 2회**까지 하고, 그래도 안 되면 반려한다. 체크리스트는 관리자 화면 승인 버튼 옆에 표시한다.
- **이유:** 관리자 2명이 기준 없이 검수하면 같은 후기를 한 명은 승인하고 다른 한 명은 반려하게 된다. 보완 횟수에 제한이 없으면 정산이 무한정 늦어진다.
- **결정 (2026-11-18):** 예시 답변대로. 관리자 최종 승인 다이얼로그에 체크리스트 4항목·보완 2회 제한 표시(`REVIEW_CHECKLIST`·`REVISION_LIMIT`).

### Q-22. 게스트가 미션을 끝까지 안 내면? — P1
- **예시 답변:** 방문 인증 후 **7일 안에 미제출하면** 운영자가 한 번 알리고, 14일이 지나면 수수료 없이 종료한다(벌점 1점). 서버에 "미제출 종료" 처리가 없으므로 당분간은 반려 처리로 대신한다.
- **이유:** 지금은 미제출 신청이 "방문 인증" 상태로 계속 남아 대시보드와 정산 대조를 어지럽힌다. 점주는 이미 손님을 받았으니, 기한을 둬야 게스트가 미션을 낸다.

### Q-23. 점주가 직접 로그인해 선정·방문 인증을 할 시점은? — P2
- **예시 답변:** M5 결과 **같은 시간에 열리는 파티가 2곳 이상**이거나 **운영자가 현장 인증을 못 한 사례가 생기면** 착수한다. 1차는 "방문 코드 입력"만 되는 점주 화면으로 시작한다.
- **이유:** 관리자 2명이 모든 현장 인증을 대신하는 구조는 업체 수가 늘면 바로 막힌다(L-A). 다만 점주 로그인은 권한 설계가 커서, 필요가 확인된 뒤 하는 게 맞다.

### Q-24. 입금 확인은 누가, 언제 하나? — P1

- **이유:** 충전을 늦게 반영하면 점주 파티의 최종 승인이 막힌다. 담당과 시간이 정해져 있어야 누락이 없다. 절차서는 partylink PR #15로 준비돼 있다.
